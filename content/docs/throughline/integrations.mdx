Throughline is deliberately a **single-block compiler**, not a full Markdown or MDX parser. Integration is simplest when your content system already identifies fenced code blocks and passes only the Throughline ones to the compiler.

For a ready-to-use setup that handles actual Markdown/MDX `thl` code fences and Fumadocs components, follow the [Markdown and MDX integration guide](/docs/throughline/markdown-mdx). For React Router, Next.js, Astro, plain Node, and non-React products, use [Other frameworks and products](/docs/throughline/frameworks).

## Two integration patterns

### Build-time compilation

For static lessons or product documentation, compile trusted authored `thl` blocks during content processing and fail the build on invalid syntax. Save or transport the resulting `Trace` to the rendering layer.

1. Parse the Markdown/MDX document using the host's Markdown parser.
2. Find fenced code blocks whose info string identifies `thl` and a supported domain.
3. Extract one block and call `compile(block)`, or pass parser-owned lines to `compileAst()`.
4. Handle `ProgramError` as a content diagnostic and report source location.
5. Send the validated `Trace` to the optional React player or another consumer.

A host parser should own document nesting, indentation, code-fence boundary detection, and the mapping of its source locations. Do not pass an entire Markdown article to `compile`.

### Runtime compilation

For interactive editors or user-authored examples, compile each submitted block in a guarded code path and display errors without crashing the page. The compiler is synchronous and bounded, but its limits are **not exact CPU-time or memory guarantees**. For potentially hostile or very frequent submissions, use the host's resource controls and consider an isolated worker appropriate to that runtime.

## When the Markdown parser gives you the block

If your host already has the block's domain, body lines, and original fence line, avoid converting back into a Markdown string:

~~~ts
import { compileAst, ProgramError, type ThlBlock } from "@0xbuff/throughline";

function compileDocumentBlock(block: ThlBlock) {
  try {
    return { ok: true as const, trace: compileAst(block) };
  } catch (error) {
    if (error instanceof ProgramError) {
      return { ok: false as const, diagnostics: error.diagnostics };
    }
    throw error; // Unexpected host or runtime failure
  }
}

const result = compileDocumentBlock({
  kind: "flow",
  lines: ['node n "Number" = 0', 'step "Set"', 'set n = 1'],
  source: { line: 12 }, // line of the opening fence in the article
});
~~~

Here, the first block-body line is treated as article line **13**. Blank lines and comments inside the block do not erase original line offsets.

A parser-supplied `ThlBlock` can also omit `source` if source mapping is unavailable. Then diagnostic line numbers are relative to the block.

## Static application / CLI without React

~~~js
import { compile, describeFrame } from "@0xbuff/throughline";

const source = 'thl callstack\nfact 3';
const trace = compile(source);

for (const frame of trace.frames) {
  console.log(describeFrame(frame, trace.frames.length));
}
~~~

No browser globals, React, service credentials, or remote APIs are required for this workflow.

## React / SSR hosts

For a React 19 application:

~~~tsx
import { useMemo } from "react";
import { compile } from "@0xbuff/throughline";
import { ThroughlinePlayer } from "@0xbuff/throughline/react";
import "@0xbuff/throughline/styles/throughline.css";

export function TraceBlock({ source }: { source: string }) {
  const trace = useMemo(() => compile(source), [source]);
  return <ThroughlinePlayer trace={trace} />;
}
~~~

This sample assumes **validated** source and is deliberately minimal. A real authoring/editor experience should catch `ProgramError` before rendering the component or handle it through the host's error boundary. Avoid using untrusted source directly in a render loop or recompiling it on every frame change.

When rendering server-side, the core compiler stays React-free; the player uses browser-only measurement and sound in effects. Respect your framework's server/client component boundary. Import player CSS explicitly and once.

## Rendering data safely

- Treat captions and labels as **plain text**, not HTML. The built-in React player does this.
- Do not execute text in `flow` or the restricted `bindings` language. Compilation is a model transformation, not evaluation.
- Only supported entry points should be imported; do not access package internals to bypass validation.
- Do not rely on the absence of compilation errors to validate unrelated Markdown, lesson policy, or instructional accuracy.
- If persisting traces, carry the `version` property and verify it when reading; schema `1` is independent of package release `0.0.2`.

## Troubleshooting integration

| Symptom | Likely reason | Action |
| --- | --- | --- |
| `Expected a thl <domain> block` | Full Markdown, wrong fence language, or missing header passed to `compile()` | Extract one `thl` block |
| `Unknown domain` | A domain outside the supported five | Choose a supported domain |
| React peer dependency error | React player imported without React 19 peers | Install compatible `react` and `react-dom` |
| Player looks unstyled | Opt-in CSS was not imported | Import `styles/throughline.css` once |
| Playback keeps resetting | New trace object passed on each render | Memoize or cache the compiled trace |
| Frame content appears shorter than full data | Value view truncation for legibility | Open **Inspect state** |

For error handling and quantitative ceilings, see [Errors and limits](/docs/throughline/errors-and-limits).
